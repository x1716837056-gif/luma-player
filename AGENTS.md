# Project workflow

- Preserve the existing Luma design and local/NAS media-library behavior.
- Treat media folders as read-only. Keep credentials, library databases, viewing history, local caches, and runtime binaries out of Git.
- Real-media acceptance tests must prefer the user's explicitly supplied test library, cataloged privately in verification-local/media-fixtures.json (roots in verification-local/media-roots.json). Re-probe those roots with scripts/catalog-test-media.py when needed. Select fixtures by verified codec, HDR/DV profile, audio and subtitle roles, not filename claims. Use temporary application profiles and disable scraping/folder watching; never copy or modify the original media. Synthetic fixtures remain useful for isolated automated tests but do not count as real-film compatibility validation. Keep the private inventory and screenshots out of Git; if the drive is unavailable, report the missing coverage.
- Run checks appropriate to each change before committing. For application changes, use the unit tests, TypeScript build, and relevant browser or Electron smoke checks.
- The user requested GitHub synchronization for future updates. After completing and verifying an authorized project change, commit the relevant source changes and push to the configured GitHub origin. Do not include unrelated work or secrets. If authentication or the network blocks synchronization, report that clearly and retain the local commit for retry.

Keep source synchronization as requested, but publish binaries and create a GitHub Release only when the user explicitly asks to publish. Avoid self-extracting portable EXEs and measure packaged startup; never label a stale binary as a newer application version.
