# Project workflow

- Preserve the existing Luma design and local/NAS media-library behavior.
- Treat media folders as read-only. Keep credentials, library databases, viewing history, local caches, and runtime binaries out of Git.
- Run checks appropriate to each change before committing. For application changes, use the unit tests, TypeScript build, and relevant browser or Electron smoke checks.
- The user requested GitHub synchronization for future updates. After completing and verifying an authorized project change, commit the relevant source changes and push to the configured GitHub origin. Do not include unrelated work or secrets. If authentication or the network blocks synchronization, report that clearly and retain the local commit for retry.
- The user also requested an EXE release with each future application update. Build and verify the Windows x64 NSIS installer and unpack-once ZIP, then publish them with release notes and SHA-256 checksums on GitHub Releases. Keep the installer asset name Luma-Windows-x64.exe for the latest-release URL. Avoid self-extracting portable EXEs: the user requires a roughly three-second startup experience, so launching must not extract the bundled runtimes each time. Measure time to the loaded, painted library with the packaged app, including fresh-profile and offline-source cases. Never publish a stale binary under a newer application version.
- The user explicitly requested public visibility on 2026-10-24. The active repository is https://github.com/x1716837056-gif/luma-player; keep future updates synchronized there and preserve its public visibility. Do not force-push, rewrite published history, or publish releases without a task that calls for it.
